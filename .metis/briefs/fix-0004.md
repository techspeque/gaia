# fix-0004 — A node returning from an outage stalls: gaia nodes times out for about 15 s after re-registration

- **Type:** fix | **Risk:** high | **Priority:** p0
- **Coder:** claude-code/opus-5-5 | **Date:** 2026-11-28
- **Plan:** .metis/plans/phase-0-plan.md Workstream 0.7: Node role, registration and heartbeat

## Goal

A node that comes back after an outage reaches the host again quickly,
well inside the Human's 30 s recovery bound (2026-11-28), and while it is
still re-establishing, a forwarded request is answered promptly with what
is happening, not held for the CLI's full timeout with a bare
"context deadline exceeded" (findings f-012, f-017).

## Cause (established before any fix)

Every time tsnet starts, it gets a new disco key. When the control server
tells the host about the restarted node's new key, the host's engine
(tailscale.com v1.98.8, `wgengine.userspaceEngine.Reconfig`, "See if any
peers have changed disco keys ... remove the peer from wireguard-go to flush
its session key") removes the peer from wireguard-go and drops the session.
If the node has already handshaken and registered by then, the node keeps
sending on the session the host has dropped. The host discards those packets
without telling the node. The host only answers nodes and never sends to
them first, so it starts no handshake. The node recovers only when
wireguard-go's `expiredNewHandshake` timer fires after
`KeepaliveTimeout + RekeyTimeout` = 10 s + 5 s = 15 s of sending without
an answer. That is the "about 15 s" in the findings. The order matters,
which is why an immediate restart does not stall: there, the host learns the
new key before the node's first handshake.

Evidence, from a scratch experiment against the local test control server
(`nettest.StartControl`, not committed). A TCP proxy in front of the control
server held the host's control stream while the node restarted, so the host
learned the new disco key only after the node's first exchange.
- Without a fix: the next request on the node's existing connection took
  17.3 s. Host log: `wgengine: Reconfig: [..] changed from "discokey:..." to "discokey:..."`.
  Node log: `Retrying handshake because we stopped hearing back after 15 seconds`.
- Without holding the stream (the host learns the key first): no stall. Requests
  took 1-2 ms, like the immediate restart in f-012.
- Tailscale's own remedy, a TSMP disco-key advertisement that lets the host
  skip the flush, is off unless the control server sets the
  CacheNetworkMaps knob (`magicsock.maybeSendTSMPDiscoAdvert`, #20081), so
  it cannot be relied on.
Why Tailscale's control server delivers the key late after a 40-45 s outage
but not on an immediate restart is not visible from here. The fix does not
depend on it.

## Fix

1. Host: `(*net.Tailnet).ResumeRestartedPeers` watches the host's netmap on
   the IPN bus. When a peer's disco key changes, it TSMP-pings that peer at
   0.5, 1.5, 3 and 6 s. A ping after the flush makes the host start the new
   WireGuard handshake itself, so the session comes back in about a second,
   not 15 s. `gaia host --tailnet` runs it for the daemon's lifetime.
   This works for nodes of any version.
2. Node: `node.Link` records where the node stands with the host: joining
   the tailnet, registering, confirming (registered, first heartbeat not yet
   answered) or ready. `Run` updates it and sends the first heartbeat after a
   registration 1 s later (`ConfirmAfter`), not after a full interval, so the
   path is confirmed quickly. While the link is not ready, the forwarder
   waits at most `RecoveryWait` (3 s) for the host's response headers. If none
   arrive, or forwarding fails, it answers 503 `unavailable` with a message
   that says the node is re-establishing its connection to the host, the stage
   and for how long, and asks the caller to retry in a few seconds. In
   steady state (ready), forwarding is unchanged and there is no new timeout. A
   long-lived response whose headers have arrived is never cut off.
3. No timeout is lengthened.

## Architectural context

- `internal/net` keeps all tsnet use (ADR-0004). The new method uses
  `local.Client.WatchIPNBus` and `local.Client.Ping` only.
- `internal/node` stays tsnet-free. `Link` is plain state shared by `Run` and
  `Forwarder`. `cmd/gaia/node.go` wires one `Link` into both.
- `core.CodeUnavailable` and the existing 503 error shape are reused, so the
  CLI prints the message and exits as it does today for an unreachable host.

## Definition of Done

- The cause is stated with evidence (above).
- With the host's control stream held as in the experiment, a request on
  the node's existing connection after the host learns the new key is
  answered within 5 s (it was 17.3 s), in an automated test against the local
  test control server.
- `gaia host --tailnet` runs `ResumeRestartedPeers` while it serves.
- A forwarded request while the node is not ready gets a 503 `unavailable`
  within `RecoveryWait` plus a margin. Its message names the host, says the
  node is re-establishing its connection and gives the stage. A forwarded
  request when ready is unchanged.
- After a registration, the node's first heartbeat goes out after
  `ConfirmAfter`, and the link turns ready when it is answered. A failed
  heartbeat turns it back to registering.
- `metis verify --post` is green.

## Manual check (real machines, as in the Phase 0 gate)

Stop the node service for 45 s, start it, then run `gaia nodes` on the node
every second for 30 s. Expect at most a few answers of "re-establishing its
connection to the host" (each within about 3 s, not a 10 s hang; the exit
code stays 99, as the CLI maps every daemon error but version mismatch today), then normal answers, all
within 30 s of start. The host log shows "peer ... restarted; renewing its
WireGuard session".
